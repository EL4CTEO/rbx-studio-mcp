# v0.9.0 scope review

The local Projects checkout started on clean main at `14714d04249f3ee86ea58676c454f855c7185b04`, matching origin/main and [v0.8.7](https://github.com/EL4CTEO/rbx-studio-mcp/releases/tag/v0.8.7). Both the package and plugin reported 0.8.7. The proposed update keeps all 35 tool names and adds no provider integrations, AI calls or cloud requirements.

## The weaknesses that justify changes

1. **The wrong view of a running game.** Discovery and UI auditing were tied to the selected Studio DataModel. Replicated server data does not include client-only UI, local state or the player's final layout. Snapshot render counters from a playtest server are not evidence about the renderer.
2. **Incomplete results with no recovery.** Execution previews discard entries and shorten strings before the MCP formatter receives them. Raising the outer response budget cannot recover that data. Rerunning a query is especially dangerous when it also performs mutations.
3. **Visual observations lack an address.** Agents can take screenshots, but connecting a screenshot point to an object requires camera math and another execution. Cropping by a server-resolved path cannot reach a client-only element.
4. **Names are insufficient identity.** Duplicate siblings and later renames/reparenting make repeated edits fragile. Indexed paths help, but indices are not a promise that the same instance remains at that address.
5. **A snapshot misses transitions.** Short-lived GUI, attribute or child changes can explain a broken flow and vanish before the next inspect call. Temporary client execution listeners disappear when their relay is removed.

Client console diagnostics, console cursors, returned playtest runtime IDs, find property projections, batched edits, script revisions, subtree sync exports and sourcemaps already exist. They are useful foundations, not new feature proposals.

## Recommended scope and implemented decisions

| Improvement | Why it earns its cost | Existing tool changes | Cost and limits |
|---|---|---|---|
| Actual-client observation | Reads the state the player sees, with the same paging, filters and projections agents already know. Adds actual render counters to the existing snapshot instead of a second profiling product. | target/player on tree, inspect, find, viewport reads and performance snapshot; shares existing readers | Small schemas; one temporary relay per read, plus one cached module folder per player/runtime. Inspect can still make two probes. Initial module replication costs more than subsequent reads. No paid APIs. |
| Visual-to-instance inspection | A screenshot can lead directly to a hit address; client path crops isolate runtime UI without exporting a large GUI tree. | viewport pick and playtest screenshot path | One raycast and a compact hit. Screenshot still performs the existing client capture/editor decode steps. Does not identify GUI buttons through a world ray or perform image segmentation. |
| Stable session references | Targets the same instance after rename/reparent and fails closed after deletion, eviction or use in the wrong VM. Makes subsequent edits safer without changing the authored place. | Optional discovery handles; existing path resolver accepts handles | One extra string per requested row. At most 5,000 strong references per VM, because weak Lua wrappers were unreliable in Studio. High query churn can evict an old handle; callers must re-query. |
| Recoverable execution previews | Retains the original result before preview clipping, so an agent retrieves only needed fields or missing pages instead of rerunning code. | execute_luau resultId/path/offset/limit/fields | At most 8 snapshots, 128 KiB each, TTL 120 s, depth 16 and 10,000 nodes per VM. Pages stay around 10 KB; default 25 rows. Copying large results adds CPU and up to roughly 1 MiB serialized cache data per VM, plus table overhead. Retention loss is explicit. |
| Bounded temporal observation | Records the transition that explains a failure while input or execution runs concurrently. Provides reusable setup, bounds and cleanup for listeners an agent otherwise rewrites. | debug watch | 1–15 s blocking window; additive listeners; initial/event data capped at 10 KB, 100 events, values at 512 bytes. Initial baseline has its own 5 KB ceiling. Every completion/error disconnects listeners. No persistent subscription protocol. |

Client-side tree/inspect/find are the strongest original candidate. Actual-client UI auditing is worthwhile because it reuses the existing auditor. Client performance snapshot is a modest extension, not a reason to invent a full profiler. Watch is useful only with bounded output, cleanup and an honest description of what signals mean. Pick, handles and recoverable results address the concrete development session failures more directly than generic convenience wrappers.

The module cache warning remains important: studio execution observes instances from the selected session but does not become the game's server VM. Execution now reports its context, VM and identity. Actual-client execution uses the client's live module cache. A new actual-server VM execution mode is deferred.

## Reliability and compatibility gates

- Keep existing write/undo fallback behavior during playtests and script revision protection.
- Keep bare duplicate paths and existing dot-containing-name resolution compatible.
- Never store handle IDs or editor/runtime pairing attributes on the authored game.
- Use cached client reader modules for shared handles/results, lazy requires inside the dispatcher, and compile/check every embedded relay and clone dependency.
- Verify real Studio behavior as well as stubs. The live tests cover temporary runtime writes, duplicate siblings, client-only UI, both GUI inset modes, crop pixels, handles, result recovery, watch events and final cleanup.

Roblox documents ScreenGui absolute positions relative to CoreUISafeInsets, which matters even when IgnoreGuiInset is enabled. The crop conversion must translate that origin rather than infer it from the layout option. [GuiBase2d documentation source](https://github.com/Roblox/creator-docs/blob/main/content/en-us/reference/engine/classes/GuiBase2d.yaml).

Watch records engine signal notifications rather than script attribution. Physics-driven properties and deferred notifications are not a promise of every intermediate value; use game instrumentation or an explicit sampler when that is required. [Roblox signal documentation](https://github.com/Roblox/creator-docs/blob/main/content/en-us/reference/engine/classes/Object.yaml).

## What should not be added now

- **A grid/spatial-query framework.** Collision tools cover individual casts and overlaps; a batch or grid can be expressed in one Luau execution. A generic grid/filter/highlight/result DSL would add schemas and edge cases before a reusable unmet need is demonstrated.
- **Named clone-and-restore checkpoints.** Cloning is not a safe scoped restore of references, Terrain, scripts, editor text and concurrent user changes. Existing undo, sync files and revision guards are better foundations. A reliable transaction preview/restore design needs separate research.
- **An internal code-understanding engine.** Sync already emits a sourcemap for luau-lsp. Dependency graphs, refactoring, semantic search and agent planning belong with the client's file/LSP tools; regex require parsing would be misleading.
- **A new server VM executor, step debugger or MicroProfiler export suite.** These introduce different permission, lifecycle or unsupported API problems. Do not imply plugin require reads the running server's module state.
- **Persistent watches, replay, test runners or assertion DSLs.** Bound observations and existing playtest/input/execute tools are sufficient for this release. Test orchestration belongs with the agent.
- **Provider-specific helpers, model calls, screenshot analysis APIs or paid telemetry.** None is necessary to expose the missing Roblox runtime evidence.
- **Reintroducing already-shipped console/cursor/runtime-ID/sync features.** Improve verified defects in those implementations, not their feature count.

## Remaining design debt

The tool descriptions repeat broad guidance and sometimes contain long measured caveats. They cost context even when the tool is unused. Shortening them is worthwhile, but correctness warnings should be preserved and measured client behavior checked before moving all guidance to one location.

The serialized tools/list array in this build is 140,628 UTF-8 bytes. That is still large; keeping 35 names does not make the manifest small. This release adds reader/recovery parameters rather than duplicating tool definitions, but it does not claim a reduction in the manifest's size or a measured provider token saving.

Queries still observe a changing live DataModel; handles secure identity, not a frozen whole-project view. UI audit remains a heuristic for clipping, small text and overlaps, not a complete visibility/occlusion or accessibility verifier. Snapshot Stats are a point-in-time observation, not frame-time percentiles. Recoverable execution snapshots are currently attached to successful clipped results; failed execution output keeps the existing bounded preview.

Picking uses the camera at query time; a moving camera can make an older screenshot's coordinates stale. Folder crops inherit the existing bounded part scan and approximate bounds. Very long result addresses fail explicitly at the page budget. Strong handles can keep detached instances referenced until lookup, eviction or the end of their VM scope.

Shipping these five extensions with explicit limits is a better 0.9.0 than adding a tool for every proposed workflow. Validation results and their practical limits are recorded separately in `v0.9.0-validation.md`.
